# 스피논 청크 기반 OTA 설계 초안

**상태:** 목표·계약 초안. 배포 클라이언트·서버는 아직 구현하지 않았다.

## 목표

React Native 앱에서 가능한 JS·스타일·이미지 OTA를 기본 범위로 삼는다. 스피논은 기능별 청크와 콘텐츠 해시를 사용해 변경된 파일만 내려받고, 특정 기능의 변경을 선택한 채널·사용자 집단에 공개할 수 있어야 한다. `부분별 배포`는 전송량과 공개 범위를 줄이는 기능이다. 기기에서 서로 맞지 않는 버전을 섞어 실행하는 기능이 아니다.

## 산출물과 경계

```text
앱 바이너리: V8 + Rust UI 코어 + GPU 렌더러 + OS 호스트 + 내장 릴리스
릴리스 스냅샷: 루트 매니페스트 + 진입점/기능 청크 + Stylo CSS + 폰트·이미지 에셋
전송: 기기에 없는 해시의 파일만 다운로드
활성화: 검증된 스냅샷 하나를 원자적으로 선택
```

그래프 본문은 앱 ID·플랫폼/CPU ABI·바이너리 `runtimeId`·그래프 형식 버전·snapshot ID, 기능 진입점과 청크 의존성, JS/CSS/폰트/이미지 객체의 SHA-256·크기를 가진다. 로컬 loader와 원격 릴리스는 이 그래프 본문을 공유한다. 원격 릴리스는 여기에 release ID·순서·서명 envelope를 덧붙인다. 필드와 호환 경계의 제안은 [R15 내부 모델](../spec/internal/0013-r15-ota-chunk-compatibility.md)에 있다. 실제 공개 wire schema·서명 알고리즘·키 운영은 D02에서 확정한다.

Vite와 Rspack의 청크 형식 차이는 빌드 어댑터가 스피논 배포 형식으로 정규화한다. 빌드 도구의 우연한 파일명이나 청크 분할 결과를 공개 호환 계약으로 삼지 않는다. 모바일 모듈 로더는 활성 스냅샷의 로컬 캐시에서 의존 청크를 해결하고 동적 `import()`를 연결한다. 네트워크에서 받은 JS를 별도 검증 없이 즉시 평가하지 않는다.

## 기능별 배포와 활성화

1. 발행자는 변경 의도인 `changedFeatureIds`를 표시할 수 있고, 빌더는 기준·목표 그래프의 diff에서 `affectedScope`와 `affectedFeatureIds`를 계산해 전체 그래프를 가진 새 릴리스 스냅샷을 만든다. closure diff는 entry·노드·객체 연결·typed edge 종류/specifier/순서를 비교한다. 기준이 없는 신규 채널에만 `baseSnapshotId` 생략을 허용한다. 최초 발행은 `affectedScope=app`이고 모든 목표 객체를 baseline diff상 신규로 기록하지만, 서버의 content-addressed 객체 저장소에 이미 있는 digest는 다시 올리지 않는다. 안전한 diff를 입증하지 못하면 app 범위와 목표 객체 전체를 후보로 사용한다. C02가 원본 import와 자원 의존성을 완전하게 추출한다는 fixture를 제공해야 한다. 구조 검증만으로 빠진 소스 import를 알아낼 수는 없다.
2. 배포 서비스가 대상 플랫폼·런타임 ID·채널·사용자 집단에 스냅샷을 할당한다. 한 기능만 변경했어도 루트 매니페스트는 새 릴리스 ID를 가진다. 기준이 없는 신규 채널에만 `baseSnapshotId` 생략을 허용한다. publish는 채널 head가 서명된 base ID와 같은지 원자 비교·갱신해 동시 발행의 lost update를 막는다. stale 기준이면 publish를 거부하고, 발행자가 최신 그래프에 의도한 변경을 다시 적용해 새 전체 목표를 검증하도록 한다.
3. 클라이언트가 새 manifest의 서명과 앱/플랫폼/ABI/`runtimeId` 호환성을 검사한 뒤 목표 graph에 도달 가능한 모든 객체 중 로컬에 없는 검증 digest 객체만 내려받는다. 첫 모델에서 정적·동적 청크의 객체를 모두 활성화 전에 확보하며, 동적 import는 실행만 지연한다. import 시점 네트워크 다운로드는 미지원이다. 압축 전송 크기·압축 해제 크기·압축률·처리 시간은 각각 상한을 둔다. 목표 전체가 준비될 때까지 기존 스냅샷을 사용한다.
4. 다음 앱 시작 또는 안전한 전체 재시작에서 새 스냅샷을 원자적으로 활성화한다. 그 뒤 기능 화면을 처음 열 때 해당 청크를 지연 로딩할 수 있다.
5. 시작 실패나 필수 기능 오류가 확인되면 같은 runtime ID의 이전 스냅샷 또는 앱에 내장된 릴리스로 되돌리고 해당 릴리스의 자동 재시도를 중단한다. 이전 snapshot 복귀는 오래된 envelope 재생이 아니라 더 높은 순서와 유효한 서명을 가진 새 롤백 명령으로 처리한다. D04는 설치를 직렬화하고 포인터 전환 직전 sequence를 다시 검사해 늦게 도착한 구버전을 거부한다. 세부 health 조건·sequence 범위·채널 이동·anti-replay는 D02/D04에서 정한다.

기능별 롤아웃은 변경된 기능과 그 공유 의존성 영향 범위를 기록하고, 앱 설치 단위의 대상 집단(cohort)에 새 **전체 목표 스냅샷**을 공개하는 방식이다. `changedFeatureIds`는 발행자의 변경 의도이고, 실제 영향은 `affectedScope`와 기준·목표 그래프 diff에서 계산한 `affectedFeatureIds`가 나타낸다. `affectedScope=app`은 최초 발행 또는 안전한 diff 불가를, `features`는 검증된 기능 closure diff를 뜻하며 cohort는 항상 앱 설치 단위다. closure 비교는 진입점, 동작 관련 노드 필드, 객체 연결, typed edge 추가·삭제·종류·specifier·순서를 포함한다. 매니페스트 내부 검증은 원본 코드에서 import가 빠졌는지 알아낼 수 없으므로 C02가 번들러의 해석된 의존 그래프를 완전하게 추출한다는 근거와 fixture를 제공해야 한다. manifest는 변경되지 않은 나머지 기능도 기존 digest 참조로 포함한다. 기능 사용 여부를 기준으로 서로 다른 릴리스의 기능 버전을 기기에서 조합하지 않는다. 공유 코드 변경은 그 청크를 참조하는 모든 기능을 영향 범위에 넣는다. 활성화된 V8 모듈의 실행 중 교체와 화면 상태 보존은 개발 HMR 및 별도 후속 연구 범위다.

## 호환성·안전 조건

- OTA 가능: 기존 바이너리의 엔진·호스트 API·Stylo와 호환되는 JS 청크·CSS 자원, 이미지·폰트 등 허용된 에셋. 외부 네트워크 CSS `@import`·`url()` 로더는 미구현이며 모바일에서 요청하지 않는다.
- 바이너리 재배포 필요: V8·Rust/GPU 코어·OS 연결·네이티브 모듈·권한 또는 현재 바이너리가 지원하지 않는 manifest/서명 검증 기능 변경. 이미 신뢰된 체인 안에서 서명 키를 교체하는 방법은 D02 보안 계약에서 정한다.
- 서로 다른 플랫폼의 산출물을 혼용하지 않는다. 엔진·호스트 API·번들 형식이 맞지 않으면 업데이트를 거부한다.
- 매니페스트 서명과 각 원본 파일 해시·크기를 확인하고, 다운로드 중단·저장 공간 부족·손상 파일·오프라인 시작에서 기존 또는 내장 릴리스를 유지한다. D04는 streaming 압축 해제에서 전송/해제 크기·압축률·시간 상한을 적용하고 한도 초과 시 임시 객체를 삭제한다. 활성 snapshot과 anti-replay high-water는 함께 원자 커밋하거나 journal 복구를 보장해야 한다. 앱 데이터 복원·초기화·재설치 뒤 anti-replay 상태가 되돌아갈 수 있는 경우와 오프라인 허용 범위는 D02/D04 위협 모델에서 정한다. 서명 알고리즘·키 교체·정확한 anti-replay 및 롤백 envelope 규칙은 D02에서 정한다.
- CDN 캐시는 불변 해시 파일로 운영하고, 서버의 채널·롤아웃 설정은 별도로 변경한다. 릴리스 중지와 기기 롤백을 구분한다.
- 앱 스토어 정책이 허용하는 앱 목적·기능 변경 범위에서만 OTA를 출시한다. 정책 심사는 기술적 청크 분할과 별개다.

## 구현 관문

첫 수직 구현에서는 단일 번들로 화면·이벤트 계약을 증명하되, 패키징 API는 R15의 그래프 본문을 담은 최소 로컬 manifest를 받도록 설계한다. X01은 이 본문에 기록된 referrer 청크별 정확한 module specifier 매핑으로 청크 그래프와 동적 `import()`를 처리한다. 유한 매핑으로 표현할 수 없는 계산형 `import()`는 빌드에서 거부한다. D02는 같은 graph schema를 참조하는 서명·anti-replay release envelope를, D03은 채널·집단 rollout을, D04는 다운로드·활성화·rollback을 완성한다. 배포 관문에서는 한 기능의 JS·CSS·이미지만 변경한 업데이트를 두 모바일 실기기에 보내고, 변경된 digest 객체만 다운로드했는지 기록한다. 다운로드 중단, 공유 청크 변경, 호환되지 않는 runtime ID, 손상 파일, 시작 실패를 각각 재현해 기존 화면과 rollback을 확인한다.
