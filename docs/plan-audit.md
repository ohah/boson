# 스피논 전체 계획 적대적 검증 · 5회

2026-09-27 기준 문서와 PoC 기록을 대조한 **설계 검토**다. 새 성능 측정이나 앱 심사 결과가 아니다. [공개 로드맵](https://macstudio.tailed42f2.ts.net/spinon/roadmap.html)의 단계·관문을 함께 수정했다.

## 1회 · 제품 약속과 범위

**반례:** 첫 앱이 React·Vue·Svelte, Vite·Rspack, Tailwind 전체, OTA까지 지원한다고 읽히면 어느 기능도 검증된 상태가 되기 어렵다.

- 발견: 로드맵의 첫 앱 설명과 후속 생태계 단계의 경계가 약했다. 같은 HTML 태그를 쓴다는 약속이 DOM 전체 호환으로 오해될 수 있다.
- 수정: 첫 앱 관문은 React·Vite 단일 번들, 제한된 HTML·CSS, Android·iOS GPU 화면과 웹의 동일 시나리오로 고정했다. Vue·Svelte, Rspack, OTA는 별도 관문으로 명시했다.
- 남은 결정: 첫 공개 버전의 태그·속성·이벤트·CSS·JS API 지원 목록과 오류 형식을 버전별 계약으로 고정해야 한다. `같은 소스`는 같은 앱 코드와 데이터 흐름을 뜻하며 픽셀 일치를 무조건 보증하지 않는다.

## 2회 · 실행 구조와 되돌리기 어려운 선택

**반례:** 트리 갱신이 빠르더라도 GPU 표면이 사라졌다 돌아오거나, IME·접근성 동작이 JS 콜백 수명과 충돌하면 앱은 사용할 수 없다.

- 발견: 회전·백그라운드 복귀·표면 재생성과 GPU 자원 복구가 성능 단계에 가까웠다. 수직 구현 관문은 CSS·텍스트를 요구하면서 주요 CSS 작업을 다음 단계에 뒀다.
- 수정: 위험 단계에 표면·자원 복구 실험을 넣고, 수직 구현에 최소 CSS 계산과 표면·콜백 수명 복구를 추가했다. 실사용 단계의 CSS 작업은 최소 기능의 확장으로 바꿨다.
- 남은 결정: GPU 백엔드와 텍스트 래스터화, JS·Rust·UI 스레드 소유권, 이벤트 취소가 동기적으로 가능한 경계, 네이티브 화면 삽입 시 합성·입력 순서를 인터페이스와 작은 실험으로 정해야 한다. Rust·GPU 선택 자체가 성능 우위의 증거는 아니다.

## 3회 · 웹 문법과 빌드 체인

**반례:** Vite에서 Tailwind가 CSS를 생성해도 모바일 계산기가 `@layer`, 변수, 선택자, 단위를 처리하지 못하면 같은 클래스의 결과가 달라진다. 단일 번들이 동작해도 동적 import와 청크 로딩은 별개다.

- 발견: Tailwind가 계획의 명시적 작업으로 없었고, 단일 번들 실험이 모듈 로더 호환으로 확대 해석될 수 있었다.
- 수정: 위험 단계에 생성 CSS 판정 실험을 추가했다. 수직 구현의 단일 번들 범위를 명시하고, CSS 확장은 별도 작업으로 유지했다.
- 남은 결정: CSS 지원 단위는 클래스 이름이 아니라 **생성된 선택자·선언·값·계층**이다. Vite와 Rspack의 출력 계약, ESM·청크·에셋 URL·소스맵은 공통 테스트 묶음으로 확인해야 한다. React 어댑터의 호스트 작업이 Vue·Svelte에 그대로 맞는지도 작은 예제로 증명해야 한다.

## 4회 · 배포 정책·보안·OTA

**반례:** 서명·롤백이 완성돼도 스토어가 원격 JS의 기능 변경을 허용하지 않거나, 앱이 브라우저로 분류되면 계획한 OTA 경로를 출시할 수 없다.

- 발견: 정책 검토가 출시 전 문서 작업처럼 읽힐 수 있었고, OTA 패키지 호환 모델이 실제 OTA 구현 직전에 있었다.
- 수정: 초기 위험 단계에 바이너리 API·JS/CSS/에셋 버전 모델을 추가하고, 출시 관문에 정책상 허용된 범위라는 조건을 넣었다. OTA 작업에 단계적 배포·자동 중지를 추가했다.
- 남은 결정: Apple의 앱 심사 지침 2.5.2는 앱 기능을 바꾸는 코드 다운로드를 제한하고, 2.5.6은 웹 탐색 앱의 엔진을 규정한다. 개발자 계약의 해석 코드 조항과 앱 심사 판단을 함께 확인해야 한다. 스피논의 GPU 앱 렌더러가 어느 분류에 들어가는지 문서만으로 확정할 수 없다. Android도 원격 코드 로딩의 무결성과 정책 위험을 검토해야 한다. **OTA는 목표이지 배포 가능성이 확인된 기능이 아니다.**

근거: [Apple 앱 심사 지침](https://developer.apple.com/kr/app-store/review/guidelines/), [Apple 개발자 계약](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/), [Android 동적 코드 로딩 지침](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading).

## 5회 · 성능 주장과 완료 판정

**반례:** 스피논은 카운터만 그리고 비교 앱은 OS 기본 동작까지 처리한다면, 프레임 수치가 좋아도 프레임워크 우위라는 결론을 낼 수 없다.

- 발견: 첫 비교 단계에서 일부 지표를 미측정으로 둘 수 있게 되어 있지만 기능·입력·화면 동등성 미달 시 순위 발표 금지가 명시되지 않았다. 기존 PoC의 UIKit 화면과 iOS 시뮬레이터 수치를 GPU 실기기 성능으로 읽을 위험이 있다.
- 수정: 첫 네 구현 비교에 동등성 미달 시 순위를 내지 않는 조건을 넣었다. 관문을 실제 기기·동작 증거로 판정하도록 명시했다.
- 남은 결정: 표본 수·측정 오차·발열·주사율·화면 콘텐츠 차이, 첫 유효 픽셀의 계측법을 실험 전 등록해야 한다. `dispatch`나 프레임 콜백 시각을 화면 표시 완료로 부르지 않는다. PoC는 기술 경계의 가능성만 보여준다.

## 현재 중단 조건과 다음 구현 순서

| 중단 조건 | 확인할 증거 | 다음 조치 |
| --- | --- | --- |
| iOS 실기기에서 JIT 없는 V8 실행 불가 | 서명된 앱의 설치·JS 호출·입력·메모리 기록 | 원인 분리 후 엔진·호스트 계획 재평가 |
| 두 플랫폼 중 하나의 GPU 텍스트·입력·접근성 경계가 성립하지 않음 | 작은 화면의 터치·텍스트·IME·의미 트리 기록 | 필요한 OS 연결 구조를 재설계 |
| CSS 최소 집합으로 같은 카운터 화면을 재현하지 못함 | 웹·Android·iOS 화면과 계산된 스타일 덤프 | 작성 계약 또는 스타일 엔진 범위 축소·수정 |
| OTA가 대상 배포 정책을 통과할 근거가 없음 | 대상 스토어·앱 기능 범위별 검토 기록 | OTA 없이 바이너리 배포 가능한 경로를 유지 |
| 비교 앱의 기능·입력 조건이 다름 | 네 구현의 기능 체크리스트와 원본 트레이스 | 순위 발표를 보류하고 동등 조건부터 맞춤 |

첫 구현 순서는 **iOS 실기기 V8·GPU 위험 실험 → 공통 호스트 계약과 최소 CSS → React 카운터의 웹·두 모바일 GPU 경로 → 실사용 UI → 여러 프레임워크·번들러 → 조건부 OTA**다. 이는 작업의 선후 관계이며 각 단계의 독립 작업은 병렬로 진행할 수 있다.

## 후속 지적 · 개발 경험

사용자 후속 검토에서 HMR과 CDP 범위가 빠진 것을 확인했다. 수직 구현에 저장 후 전체 리로드·로그·소스맵 관문을 추가하고, 생태계 단계에서 HMR·프레임워크 상태 보존, V8 Inspector, 스피논 UI 트리 조사를 각각 분리했다. [개발 경험 명세](developer-experience.md)에 전송 경계와 완료 판정을 기록한다. 이 보강은 위 다섯 회차의 원래 발견 사항과 구분한다.

이어서 CLI와 MCP 경계도 빠진 것을 확인했다. 첫 앱 관문에 최소 CLI를 넣고, 구조화 출력과 로컬 MCP 진단은 후속 개발 도구 관문으로 분리했다. [CLI·MCP 설계](cli-mcp.md)에 공통 진단 모델과 공개 원격 노출 금지를 기록한다.
