# 스피논 비교 벤치마크 계획

## 목적과 비교 대상

스피논의 각 기능을 추가할 때 같은 사용자 동작을 네 구현으로 재현하고, 화면에 실제로 나타나는 결과와 자원 사용량을 함께 비교한다. 비교 대상은 다음과 같다.

| 구현 | 비교 기준 |
| --- | --- |
| 스피논 | 해당 시점의 커밋, V8 설정, 렌더링 방식과 구현된 최적화를 모두 기록 |
| React Native | New Architecture의 Fabric과 기본 Hermes를 사용한 릴리스 빌드 |
| ReactLynx | 공식 ReactLynx 도구 체인의 릴리스 빌드와 기본 런타임 설정 |
| 플랫폼 네이티브 | Android Views와 iOS UIKit으로 같은 화면·동작 구현 |

버전과 설정은 첫 비교를 실행할 때 잠근다. 이후 업그레이드 결과는 같은 표의 기존 결과를 덮지 않고 새 실험으로 기록한다. 네이티브 구현은 달성 가능한 플랫폼 기준선이며, 네 구현 간 UI 프레임워크 비용을 단독으로 분리해 주는 대조군은 아니다. React Native와 ReactLynx는 각각 다른 JS 엔진과 렌더링 구조를 포함하므로, 결과는 **전체 앱 경로**의 비교로 해석한다.

## 같은 기능으로 맞출 화면

각 시나리오는 데이터, 화면 크기, 폰트, 이미지 파일, 텍스트 길이, 동작 횟수, 화면에 보이는 행 수를 동일하게 한다. 접근성 텍스트와 최종 화면의 노드 수·내용을 확인한다.

플랫폼 기본 버튼과 GPU로 그린 버튼의 픽셀 모양이 다를 수 있다. 따라서 기능·콘텐츠·터치 영역·접근성 동작의 동등성을 먼저 확인하고, 픽셀 차이는 별도 품질 지표로 기록한다. 비교 앱 중 하나가 필요한 기능을 빠뜨리면 그 시나리오의 성능 순위를 내지 않는다.

| 순서 | 시나리오 | 사용자 동작 | 주요 관찰값 |
| --- | --- | --- | --- |
| 1 | 작은 화면 | 텍스트·버튼·행/열 레이아웃 표시, 버튼으로 노드 추가·삭제 | 첫 화면, 터치 반응, 레이아웃·GPU 제출·표시 시간 |
| 2 | 트리 갱신 | 100·1000개 노드에서 텍스트·스타일·삽입·삭제를 같은 순서로 반복 | 갱신 지연, 메모리, 프레임 지연 |
| 3 | 긴 목록 | 같은 데이터와 이미지로 고정 거리 스크롤, 행 재사용 정책을 기록 | 스크롤 프레임, 메모리 최고치, 재사용 비용 |
| 4 | 복잡한 화면 | 긴 글, 이미지, 중첩 레이아웃, 회전 | 텍스트·이미지 완료 시각, 화면 일치 |
| 5 | 계산 경합 | 같은 시간의 JS 계산과 별도 CPU 부하 중 터치·스크롤 | 입력부터 화면 변화까지의 지연, 프레임 지연 |

첫 네 구현 비교는 현재 스피논 PoC가 검증한 작은 화면과 트리 갱신을 새 Rust 코어·Taffy 경로로 옮긴 뒤 시작한다. 긴 목록·이미지·복잡한 텍스트 측정은 스피논에 해당 기능이 생긴 뒤 네 구현 모두에 추가한다. 목록은 각 프레임워크의 권장 재사용 컴포넌트를 사용한 **실사용 비교**와 재사용 조건을 맞춘 **렌더러 진단**을 별도 결과로 기록한다.

## 계측 계약

- **사용자 지표:** 콜드 시작부터 첫 유효 화면까지, 입력 시각부터 변경된 픽셀이 표시될 때까지, 스크롤 프레임 시간 분포, 지연된 프레임 수, 성공한 입력 수.
- **자원 지표:** 프로세스 메모리와 최고치, CPU 사용량, 앱 설치 크기와 JS/리소스 번들 크기. 크기 수치는 같은 ABI와 빌드 설정에서 비교한다.
- **원인 분석 지표:** JS 실행, 트리 갱신, 레이아웃, GPU 장면 생성·제출 또는 플랫폼 뷰 적용 시간을 각 구현이 제공하는 범위에서 계측한다. 내부 단계의 이름과 경계가 다르면 한 열에서 직접 순위를 매기지 않는다.
- 프레임 콜백 간격과 메서드 반환 시간은 실제 픽셀 표시 완료 시각으로 표기하지 않는다. Android는 Macrobenchmark의 시작·프레임 지표와 시스템 트레이스를, iOS는 XCTest/Instruments의 시작·hitch·signpost 지표를 우선 사용한다. 입력→픽셀 지연은 별도 화면 캡처/광학 계측 경로를 마련하고 측정 오차를 함께 기록한다.

## 실행 규칙

1. Android와 iOS를 **각각 같은 실기기**에서 네 구현으로 측정한다. 시뮬레이터 결과는 개발 중 진단으로만 남기고 실기기 순위에 섞지 않는다.
2. 릴리스 빌드, 동일 화면 밝기·주사율·전원/발열 상태, 같은 데이터와 동작 스크립트를 사용한다. 네 앱의 실행 순서를 회차마다 바꾸고 각 조건을 여러 차례 반복한다.
3. 자동 입력 전후에 앱이 실제로 전경에 있는지, 기대한 입력 횟수와 최종 화면이 맞는지 확인한다. 실패한 회차는 이유와 원본 로그를 남기고 집계에서 제외한다.
4. 중앙값과 꼬리 지연(p95), 회차별 분포를 함께 보고한다. 작은 차이는 변동 폭과 함께 판단하며 단일 숫자로 우열을 단정하지 않는다.
5. 결과에는 기기·OS·프레임워크·엔진·커밋·빌드 플래그·주사율·원본 트레이스·화면 캡처를 연결한다. **미구현**, **미측정**, **측정 실패**를 0이나 빈 값으로 대체하지 않는다.
6. 표본 수, 허용 오차, 기능 동등성 체크리스트와 화면 표시 완료의 관찰 방법을 결과를 보기 전에 기록한다. 앱이 전경에 없거나 입력·화면 검증이 실패한 회차는 성능 집계에서 제외한다.

## 현재 상태

[동적 UI 트리 PoC](../../spikes/dynamic-tree/README.md)는 Android 실기기와 iOS 시뮬레이터에서 스피논 단독으로 노드 추가·삭제, 레이아웃, 터치, 계산 경합을 확인했다. 기존 [A/B 결과](../../spikes/dynamic-tree/evidence/ab-results.md)는 스피논 내부의 검색 방식 비교이며, [경합 결과](../../spikes/dynamic-tree/evidence/contention-results.md)는 프레임 콜백 간격 측정이다. 둘 다 이 문서의 네 구현 간 성능 순위로 사용하지 않는다. 첫 비교 결과는 네 구현의 작은 화면 앱과 동일 계측 경로가 갖춰진 뒤 작성한다.
