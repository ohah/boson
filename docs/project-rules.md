# 스피논 필수 프로젝트 규칙

스피논 저장소에서 작업하는 에이전트와 개발자는 이 규칙을 따릅니다. 구현 상태의 공식 원본은 [상태 대장](../spec/STATUS.md), 공개 동작 계약의 원본은 [명세 인덱스](../spec/README.md)에서 연결한 `spec/` 문서입니다.

## 문서와 언어

- 문서·사용자 설명·코드 주석·PR 리뷰 코멘트는 한글로 작성합니다. 식별자, API 이름, 명령어, 외부 프로젝트 고유명은 원어를 유지해도 됩니다.
- 커밋과 PR 제목의 타입·범위 접두어는 영어로 쓰고, 그 뒤의 제목과 본문은 한글로 작성합니다. 예: `feat: 기능 설명`, `docs: 문서 설명`, `feat(docs): 문서 기능 설명`.
- 작업 미리보기의 개인 체크 상태나 비규범 대응표를 공식 구현 상태 또는 지원 계약으로 취급하지 않습니다.

## 구현과 근거

- 기능 구현이나 동작 수정을 시작하기 전에 기준 구현 또는 독립 oracle, 재현 입력·환경, 관찰값, 사전 판정 기준을 정하고 [구현 전 비교 모델](../spec/0001-conformance.md#구현-전-비교-모델)과 작업 fixture에 기록합니다. 직접 비교할 기준이 없으면 명세 기반 예상값·불변 조건과 한계를 먼저 기록합니다.
- PoC에서 확인한 동작과 완성된 제품 기능을 구분합니다.
- 성능 주장은 기기·빌드·입력 조건과 원본 로그를 연결하고, 시뮬레이터 결과와 실기기 결과를 분리합니다.
- 구현 항목을 완료로 표시할 때는 [상태 대장](../spec/STATUS.md)의 해당 ID를 갱신하고, 같은 변경에서 공개 API 또는 내부 인터페이스의 버전 있는 명세·예제·오류·플랫폼 차이·동작 근거를 연결합니다. API 명세 없이 완료 체크를 하지 않습니다.
- 조사·벤치마크처럼 호출 가능한 API가 없는 항목은 판정 기준·산출물·원본 근거를 연결합니다.
- 구현이 명세와 다르거나 새로운 제품 결정이 필요해지면 차이와 선택지를 사용자에게 알립니다. 미정인 계약을 지원 기능처럼 게시하지 않습니다.

## PR 적대적 검증

- 모든 PR은 병합 전에 서로 다른 관점의 적대적 검증 20회를 거칩니다. 구현·문서·설계 변경에 맞게 검토 항목을 고르되, 같은 내용을 말만 바꾸어 반복하지 말고 각 회차에서 별도의 실패 경로·불변 조건·계약 경계를 확인합니다.
- 가능한 경우 실제 코드·고정된 의존성 버전의 공식 문서·fixture·실행 근거를 대조합니다. 변경 범위와 무관한 검사를 억지로 적용하지 않으며, 실행하지 않은 빌드·테스트·플랫폼 검증은 통과했다고 보고하지 않습니다.
- 결함을 찾으면 수정한 뒤 영향받는 검토 관점을 다시 확인합니다. PR 본문에는 검토 횟수 대신 실질적인 발견·수정·남은 한계를 씁니다.

## Rust 코드 구조와 도구

- Rust 소스 파일은 보통 300~500줄을 권장 상한으로 삼습니다. 500줄을 넘기면 책임 경계를 기준으로 나눌 수 있는지 먼저 검토하고, 예외를 둘 때는 파일이 한 책임으로 응집되어 있는 이유를 PR에 적습니다.
- 모듈은 자료형·변경 로직·snapshot·플랫폼 경계·테스트처럼 역할에 따라 나누고, 가능한 한 내부 가시성으로 경계를 유지합니다. 줄 수만 맞추려고 작은 파일을 양산하거나 응집된 코드를 억지로 쪼개지는 않습니다.
- Rust 이름은 관용 규칙을 따릅니다: 모듈·함수·변수는 `snake_case`, 타입·trait·열거형 variant는 `UpperCamelCase`, 상수는 `SCREAMING_SNAKE_CASE`로 씁니다.
- 복구 가능한 실패는 `Result`와 구체적인 오류 타입으로 전달합니다. `expect`는 이미 검증된 내부 불변 조건처럼 복구가 불가능한 지점에만 쓰고, 이유를 메시지에 남깁니다.
- `unsafe` 경계는 필요한 범위로 좁히고, 공개 unsafe 함수에는 `# Safety` 계약을 한글로 적습니다. FFI의 포인터 유효 범위와 소유권은 호출자 계약에 드러냅니다.
- 코드 서식의 기준은 저장소 루트의 `rustfmt.toml`입니다. Rust 코드를 바꾼 뒤 `cargo fmt --all -- --check`를 실행합니다.
- Rust formatter는 `rustfmt`, linter는 `Clippy`를 사용합니다. 기본 lint 명령은 `cargo clippy --locked --workspace --all-targets -- -D warnings`입니다. 경고를 무시하는 광범위한 `allow` 대신 원인을 고치고, 예외가 꼭 필요하면 적용 범위와 이유를 바로 옆에 기록합니다.

## GitHub 라벨

- 모든 GitHub 이슈와 PR에는 작업 유형 라벨과 주요 영역 라벨을 각각 하나 이상 지정합니다. 기존 라벨이 맞으면 재사용하고, 비슷한 라벨을 중복해서 만들지 않습니다.
- 필요한 라벨이 없으면 이름과 적용 범위를 먼저 사용자와 논의한 뒤 만듭니다. 라벨 설명은 한글로 씁니다.

## Git과 문서 배포

- 기본적으로 작업 브랜치와 PR에서 변경을 검토합니다. PR 본문에는 [양식](../.github/pull_request_template.md)에 따라 변경한 상태 ID, 명세, 동작 근거와 남은 범위를 기록합니다.
- `main`에는 직접 푸시하지 않고 PR을 거칩니다. GitHub 보호 설정에서 관리자에게도 PR 경유와 선형 이력을 요구합니다.
- PR은 `Rebase and merge`로 병합합니다. 개별 커밋을 `main`에 남기고 머지 커밋을 만들지 않습니다. `Squash and merge`와 `Create a merge commit`은 사용하지 않습니다. GitHub의 리베이스 머지는 커밋 SHA를 새로 만들므로, 원래 SHA를 보존해야 하는 참조는 병합 후 확인합니다.
- 첫 공식 릴리스 전까지 문서 사이트는 자동 배포하지 않습니다. [Pages 워크플로](../.github/workflows/docs-pages.yml)는 수동 실행만 허용하며, 사용자가 명시적으로 요청하지 않으면 실행하거나 `gh-pages`를 갱신하지 않습니다. 개발 중 미리보기는 사용자가 정한 별도 경로를 따릅니다.
- 스피논의 첫 공식 릴리스가 나오기 전까지 RSPress(`@rspress/core`) 버전 `2.0.22`를 업데이트하지 않습니다. 문서 작업에서도 `packages/docs/package.json`과 `bun.lock`의 RSPress 버전을 유지합니다.
