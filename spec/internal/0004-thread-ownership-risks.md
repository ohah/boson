# 내부 검토 0004 · R06 스레드·소유권 위험 분석

**상태:** 검토 초안 · **공개 API:** 아님 · **구현 완료:** 아님 · **상태 대장:** R06 미완료

이 문서는 현재 V8·Rust FFI·트리·GPU 경계를 대조해 위험과 후보 실행 규칙을 모읍니다. 표의 권고는 구현 전 검증할 후보이며, 사용자 승인이나 제품 계약을 대신하지 않습니다. 이 문서를 추가해도 V8 동시 호출, 비동기 Fetch, 취소, 실기기 경합을 구현하거나 시험한 것은 아닙니다.

## 현재 코드에서 확인한 경계

| 경계 | 저장소에서 확인한 동작 | 이 사실만으로 확인되지 않는 것 |
| --- | --- | --- |
| 앱 진입 | Android JNI와 iOS Objective-C++가 `spinon_app_run()`을 동기 호출합니다. 반환 전 V8 생성·평가·이벤트 전달·해제가 끝납니다. | 호출자가 항상 같은 OS 스레드인지, 장기 런타임에서 호출 순서가 보장되는지 |
| V8 핸들 | `SpinonV8Runtime`이 Isolate·Context·이벤트 함수의 `Global` 핸들을 보유합니다. `eval`, `dispatch`, `free`는 호출 스레드에서 직접 V8 API를 사용합니다. | 호출자 스레드 검사, 작업 큐, 동시 호출 차단, 앱 간 런타임 격리 |
| Rust 콜백 | C++은 JS 실행 중 Rust 콜백을 동기 호출합니다. `user_data`는 `spinon_app_run()` 지역 `CallbackState`를 가리키며 런타임이 반환 전에 해제됩니다. | 콜백을 비동기 보류하거나 실행 도중 런타임을 닫을 때의 안전성 |
| Rust 트리 | `Tree::commit(&mut self, ...)`는 기준 revision을 검사하고 후보 복사본 전체를 검증한 뒤 원자적으로 바꿉니다. 내부 잠금이나 외부 호출 직렬화는 없습니다. | FFI에서 공유할 때의 동기화, HostDocument의 스레드, 다중 Owner의 재동기화 |
| 문서 호스트 제안 | R03은 동기 DOM 논리 조회·변경, 원자 묶음, Isolate 작업 큐를 제안합니다. 전역 `DocumentRevision` 때문에 다른 `OwnerId`의 독립 변경도 오래된 묶음이 될 수 있음을 미결정으로 남겼습니다. | 실제 큐 용량·정체성·종료, revision 충돌 복구, 프로미스 완료와 취소의 승자 규칙 |
| GPU 경계 | R13 실험의 wgpu 렌더러 핸들은 해당 실험에서 UI 스레드에 직렬 호출합니다. R13 문서는 동시 draw·resize·destroy 및 실제 비동기 장치 손실 경합을 시험하지 않았다고 명시합니다. | 모든 플랫폼 GPU 백엔드가 같은 스레드를 써야 하는지, 미래 렌더러와 런타임 사이의 전체 수명 규칙 |

V8 헤더는 다중 스레드 환경에서 Isolate 사용을 `v8::Locker`로 직렬화하도록 설명합니다. Isolate는 어느 스레드에서도 진입 중이지 않을 때만 `Dispose()`할 수 있고, 고정 리비전의 API는 다른 스레드에서도 `TerminateExecution()`을 호출할 수 있다고 설명합니다. 이는 사용 가능한 V8 API의 사실이지, 스피논의 취소·종료 정책이나 현재 안전성이 아닙니다. 자세한 소스 대조는 [R06 소스 감사 기록](./evidence/r06-thread-ownership-source-audit-2026-09-29.md)에 있습니다.

## 후보 실행 경계

초기 구현에서 데이터 소유권을 단순하게 유지할 후보 구조입니다. 전용 스레드의 수, UI가 동기 대기할 수 있는 호출, 취소 의미는 아래 미결정 사항과 검증 관문을 통과하기 전까지 고정하지 않습니다.

```text
플랫폼 UI·입력 스레드 ── 입력 메시지 ──┐
GPU 표면 소유 실행기  ← 완성 스냅샷 ──┤
                                      ▼
                     런타임 직렬 실행기
                     ├─ V8 Isolate·Context·Global
                     ├─ Rust HostDocument 변경·동기 논리 조회
                     └─ JS 콜백·Promise 정착
                                      ▲
타이머·네트워크 작업자 ─ 소유 데이터 메시지 ┘
```

1. **런타임 소유자:** 하나의 Isolate와 그 Context·`Global` 핸들·콜백 등록부는 하나의 직렬 실행 경로가 소유합니다. 초기 후보는 Isolate마다 안정된 OS 스레드 하나를 두고 V8 호출, Rust 콜백, 마이크로태스크, 닫기를 그 스레드에서 처리하는 방식입니다. 다른 스레드에서 Isolate를 번갈아 진입하는 방식은 V8 Locker 사용, 스레드 전환, 재진입과 종료를 별도 실험하기 전에는 채택하지 않습니다.
2. **문서 소유자:** R03의 DOM 호출 후 동기 조회 의미를 보존하려면 가변 `HostDocument` 변경과 논리 조회를 런타임 소유 실행 경로에서 수행하는 안이 가장 단순합니다. 플랫폼 스레드에서 오는 입력·수명 신호는 복사 가능한 메시지로 보냅니다. UI 스레드가 V8 완료를 동기 대기하는 경로는 기본 후보에 넣지 않습니다.
3. **트리 공개:** 한 변경 묶음은 검증과 커밋이 끝난 뒤에만 스냅샷이 됩니다. 레이아웃·렌더러는 V8 핸들, `Tree` 참조, 콜백 포인터 대신 불변의 소유 데이터와 `(runtime_generation, document_revision, render_tree_revision, environment_revision)`을 받습니다. 스냅샷 계산 결과는 입력 세대·revision이 현재 화면 정책에 맞지 않으면 적용하지 않습니다. 화면 스냅샷을 합치더라도 논리 커밋을 재실행하거나 입력 이벤트를 다른 프레임 대상으로 바꾸지 않습니다.
4. **비동기 완료:** 타이머·Fetch 전송 작업자는 V8 값, `Global` 핸들, `user_data` 포인터를 만지지 않습니다. 작업자는 요청 ID·런타임 세대·결과 바이트·오류 자료를 소유 메시지로 런타임 실행 경로에 전달합니다. Promise와 JS 오류 처리는 해당 실행 경로에서만 합니다. 현재 R06은 Fetch API를 제공하거나 WHATWG Fetch 동작을 확정하지 않습니다.
5. **입력:** GPU 표면 소유 경로가 입력 시점에 마지막으로 표시한 프레임의 대상과 좌표를 기록한 뒤 런타임 실행 경로로 전달합니다. 전달 시 런타임 세대·OwnerId·노드 생존 여부를 재검증하는 안을 둡니다. 오래된 프레임 입력의 폐기, 포인터 이동 병합, 누락이 허용되지 않는 눌림·해제 이벤트의 큐 초과 정책은 이벤트 명세와 함께 결정해야 합니다.
6. **오류 경계:** JS 예외, Rust 도메인 오류, C++ 생성·플랫폼 오류는 출처와 요청 ID를 보존하는 내부 결과로 바꾸고 어느 쪽 언어의 예외·패닉도 C ABI 경계를 넘어가지 않게 합니다. 비동기 오류도 현재 런타임 세대와 대기 중 요청에 속할 때만 Isolate에 전달합니다. 메시지 문자열의 임시 포인터를 런타임 해제 뒤까지 보관하지 않습니다.

## 닫기·취소 프로토콜 후보

아래는 use-after-free를 막기 위한 실행 순서 후보이지, 지금 코드에 구현된 수명 계약이 아닙니다.

1. 런타임 관리자가 `Active → Closing` 전이를 한 번 수행하고 새 일반 작업 등록을 거부합니다. 닫기 요청에는 마지막 런타임 세대를 기록합니다.
2. 이미 실행 중인 JS 작업은 명시된 종료 정책에 따라 완료시키거나 V8 실행 중단을 요청합니다. V8의 `TerminateExecution()`은 실행 중인 JS의 외부 부수 효과를 롤백하지 않으므로, 일반 Fetch 취소와 같은 의미로 취급하지 않습니다.
3. 닫기 경계에서 대기 중인 구세대 입력·타이머·네트워크 결과를 폐기합니다. 전송 취소는 별도 작업자에 비동기로 알리고 Isolate 소유 경로에서 그 작업자의 응답을 기다리며 교착하지 않습니다.
4. Isolate 소유 실행 경로에서 Promise·이벤트 등록부와 `Global` 핸들을 정리합니다. 이 경로를 빠져나와 어떤 스레드도 Isolate 안에 있지 않음을 보장한 뒤 `Dispose()`합니다.
5. 그 뒤 Rust callback 상태와 runtime handle을 회수합니다. 늦게 도착한 결과는 세대 불일치로 JS에 전달되지 않고 자기 소유 메모리만 정리합니다.
6. GPU·표면 자원은 해당 플랫폼 그래픽 실행 경로가 별도로 정리합니다. JS Isolate 소유권을 GPU handle 수명에 섞지 않습니다.

현재 제품 계약으로 정하지 않은 부분은 (a) 실행 중 JS를 언제 강제 중단할지, (b) 단일 요청 취소와 완료가 경합할 때 어느 상태를 반환할지, (c) 종료 시 pending Promise를 거부할지 런타임과 함께 폐기할지, (d) 큐가 찼을 때 어떤 입력을 병합·거부할지입니다.

## R06 완료에 필요한 후속 검증

이 문서와 정적 소스 대조는 R06의 분석 산출물입니다. R06 상태는 완료로 바꾸지 않습니다. 다음 실험은 S03 구현 전에 별도 범위로 계획합니다.

- Android 에뮬레이터와 iOS 시뮬레이터에서 Isolate 소유 실행기, 소유 thread 기록, 동시 외부 요청 직렬화와 종료 대기를 구현·확인합니다.
- Promise/Future가 붙기 전에도 시험 가능한 가짜 네트워크 완료 메시지로 요청 완료·취소·세대 만료 경합을 재현합니다. 실제 Fetch 의미를 검증했다고 표시하지 않습니다.
- 두 Owner의 stale revision, commit 도중 오류, 지연 snapshot, 지연 입력, 닫기 중 callback을 결정된 로그 marker와 순서로 반복합니다.
- 양쪽에서 UI/그래픽 경로가 Isolate를 동기 대기하지 않고, V8 객체와 callback 자료가 소유자 밖에서 읽히지 않는지 확인합니다.
- 물리 기기에서 확인하지 못한 조건은 에뮬레이터·시뮬레이터 결과와 분리해 기록하고, R06 전체는 실기기 경합 범위가 남으면 미완료로 둡니다.

## 미결정 선택지

1. Isolate마다 실제 고정 OS thread를 둘지, 하나 이상의 런타임에서 공용 전용 실행 thread를 공유할지. 공유하면 공정성·head-of-line blocking·앱 종료 격리를 측정해야 합니다.
2. iOS·Android의 각 실행기를 어떤 원시 thread/queue API로 구현할지. 직렬 dispatch queue는 논리 직렬성만으로 V8의 물리 thread affinity를 증명하지 않습니다.
3. `HostDocument` 소유자를 JS 실행기와 같게 둘지 별도 코어 worker로 나눌지. 분리하면 동기 DOM 조회의 대기·교착·commit 순서가 추가 검증 대상입니다.
4. 전역 `DocumentRevision` 충돌을 어댑터 전체 재계산·Owner별 revision·다른 검증 가능한 방식 중 무엇으로 해결할지.
5. 우선순위 기준은 [JavaScript 작업 스케줄러 설계](0006-js-task-scheduler.md)의 Chromium 참고 방향으로 정했다. 공개 API, 플랫폼 이벤트와 내부 작업의 우선순위 매핑, 공정성, 용량, 프레임 snapshot 병합, 포인터 이동 병합, 눌림·해제 보존 및 backpressure 정책은 미정이다.
6. running JavaScript 취소, 종료 대기 시간 제한, V8 강제 종료 후 isolate 재사용 가능 여부.
7. 종료 중 pending Promise·타이머·플랫폼 모듈 요청의 결과와 오류 보고 방식.
8. 메모리 할당 실패·Rust panic·C++ 예외의 앱 복구 범위와 비동기 오류의 진단 보존 기간.
